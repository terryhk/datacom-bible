## 2. 背景与目标

### 2.1 业务背景与现状痛点

在大型企业园区网络、数据中心及校园网日常运维中，网络工程师需要对成百上千台交换机、路由器进行常态化的健康巡检与配置版本管理。传统依赖人工通过终端软件（如 CRT、Xshell）逐台登录设备敲命令巡检的运维方式，暴露出四大致命痛点：

1. **日常巡检耗时耗力，人力成本高且极易遗漏**：网络工程师每天需花费数小时手动登录各楼栋核心、汇聚与接入交换机，敲 `display` 查看电源、风扇、CPU、内存及路由邻居状态。人工查阅成千上万行回显信息极易产生视觉疲劳，导致微弱的隐患（如单电源掉电、风扇单转速停转、LACP 成员链路被误拔）未能被及时察觉，最终酿成重大宕机事故；
2. **配置文件备份不及时，灾备恢复无凭无据**：现网交换机经常因临时故障排查、业务扩容或工程师误操作而修改配置，缺乏自动化的配置版本固化机制。一旦发生物理硬件烧毁、雷击死机或恶意篡改，由于本地缺失最新日期的配置文件备份，导致业务恢复时间从几分钟拉长至数天；
3. **运维脚本缺乏工程化架构，代码“屎山化”严重**：许多网络工程师编写的早期 Python 脚本采用简单面向过程硬编码方式（把交换机 IP、密码、巡检命令全部写死在 `.py` 代码中）。只要设备增减或检查项微调，就必须重新修改核心代码，不仅代码复用率极低，且将管理凭证以明文暴露，存在巨大信息安全隐患；
4. **异常容错能力极度脆弱**：面对现场网络偶发丢包、SSH 连接超时或交换机拒绝连接等常见异常，简单脚本直接崩溃报错退出，导致后续数百台设备的巡检工作全部中断。

### 2.2 建设目标

本系统旨在基于 Python 3 与现代网络编程生态（SSH/Paramiko、SFTP、NETCONF/ncclient），面向运维跳板机（terminal01）与企业 NOC 监控中心，构建一套高内聚、低耦合、工程化可扩展的**园区网自动化运维脚本系统**：

1. **多维健康状态自动化全量巡检**：定时并发巡检全网交换机的关键硬件与网络协议状态（电源、风扇、内存利用率、CPU 利用率、OSPF 邻居状态、LACP 链路聚合状态），自动识别异常并抛出明确告警；
2. **命令与代码彻底解耦**：将所有巡检命令抽象为外部文本文件进行动态读取，代码只负责执行调度与正则匹配，新增巡检命令无需修改任何 Python 源码；
3. **自动化安全定时备份（24 小时周期）**：每隔 24 小时通过 SFTP 安全文件传输协议，将全网交换机的当前配置文件拉取备份至本地，并按照“`日期_设备名.zip/bak`”规范归档；
4. **新一代 NETCONF 自动化纳管**：利用 NETCONF 协议远程为设备配置日志主机（Syslog Server），并每隔 24 小时定期通过 NETCONF 自动同步更新全网设备时钟；
5. **面向对象（OOP）架构与防御性容错**：采用清晰的类封装（Class）、初始化方法与可变参数字典解包（`**kwargs`），全局嵌入深层异常捕获（`try...except`），确保单台设备故障不阻塞全局任务流。

## 3. 用户与场景

### 3.1 涉及角色

| 角色代码 | 角色名称 | 核心关注点与职责 |
|:---|:---|:---|
| **ROLE-01** | **NOC 自动化运维工程师** | 负责脚本系统的研发、外部命令表维护、定时任务（Crontab）编排及告警阈值配置 |
| **ROLE-02** | **现场网络值班人员** | 日常查看自动化巡检日志、接收告警输出，根据故障设备提示去现场更换电源或风扇 |
| **ROLE-03** | **网络架构师 / 安全审计员** | 定期核查历史配置文件备份归档的完整性、检查全网设备日志主机及时间同步合规性 |

### 3.2 典型用例与运行场景

```
                                [运维跳板机: terminal01]
                                ┌─────────────────────────┐
                                │   main.py (调度中心)     │
                                ├────────────┬────────────┤
                                │ 外部命令库  │ 设备凭证库  │
                                │ (commands) │ (config.py)│
                                └─────┬──────┴─────┬──────┘
                                      │            │
             ┌────────────────────────┴────────────┴────────────────────────┐
             │                      SSH / SFTP / NETCONF                     │
             ▼                                                               ▼
   [核心交换机 Core-01]                                            [汇聚交换机 Agg-01]
   - 抓取: 电源 / 风扇 / 内存 / CPU                                  - 抓取: OSPF 邻居 / LACP 状态
   - SFTP 备份: 20261110_Core01.zip                                - NETCONF: 同步时钟 / 配置 Syslog
```

1. **每日定时健康体检场景**：每天清晨 06:00，系统自动被系统调度触发，通过 SSH 并发连接至全网核心与汇聚交换机，读取指令并执行。若发现风扇转速异常，立即在控制台输出醒目的红色告警 `All fans are fault` 并记录审计日志；
2. **灾备配置归档场景**：每天深夜 02:00，脚本自动触发全网交换机保存当前配置（`save`），随后启动 SFTP 客户端拉取 `.zip` 配置文件保存至本地备份目录，按统一标准命名规则存储，保留 30 天滚动记录；
3. **时钟与日志合规性加固场景**：脚本通过 NETCONF 模块连接设备 830 端口，下发 XML 模板，将全网设备的 Syslog 主机统一指向企业日志审计服务器 `192.168.100.200`，并下发当前精确的 UTC/CST 时间戳完成时钟校验。

#### 2. 命令解耦动态读取机制
避免硬编码，从外部文本提取指令清单：

```python
def load_commands(filepath="commands.txt"):
    cmd_list = []
    with open(filepath, 'r', encoding='utf-8') as f:
        for line in f:
            cmd = line.strip()
            if cmd and not cmd.startswith('#'):
                cmd_list.append(cmd)
    return cmd_list
```

## 7. 风险与开放问题

### 7.1 现网潜在风险与规避策略
1. **多厂商命令输出格式不兼容风险**：不同华为 VRP 版本（如 VRP V5 与 VRP V8/CloudEngine）针对 `display fan` 或 `display cpu` 的回显关键字格式略有差异，可能导致固定正则解析失效。
   - **规避方案**：采用多模式容错匹配，优先使用通用关键字匹配，或根据设备系统版本动态加载对应的解析模板。
2. **SFTP 备份占用设备控制面 CPU 风险**：大型交换机保存配置（`save`）需要耗费磁盘写入与 CPU 资源，若数百台设备瞬间同时并发备份，可能影响网络控制面。
   - **规避方案**：在调度主程序中加入微秒级随机抖动（Jitter）错峰机制，平滑分流备份流量。

### 7.2 开放问题与进阶工程探索
1. **考场环境依赖库缺失避坑**：在常见离线考场或受限生产环境中可能缺少预装的特定第三方库，现场如何利用 Python 原生 Socket 或离线 `.whl` 包救急未深入展开；
2. **分布式多线程并发巡检（ThreadPoolExecutor）**：本真题基准方案主要以单线程循环结合面向对象结构展开，对于超大规模网络（千台以上）的多进程/协程高并发生产级架构未展开代码级实现。
