## 二、分述

### 2.1 数据通信基本概念与组网形态

#### 核心原理

**通信**有两个层面。广义的通信是万物之间信息传递的过程——微波、3G/4G/5G、物联网都属于"通信"的范畴。而我们数通课程所讲的**网络通信**，特指利用 IP 技术实现数据通信的过程。

网络通信有三个最基础的场景，由简到繁：

- **场景 A**：两台计算机通过网线直连——最简单的点到点网络。
- **场景 B**：引入路由器，把不同终端连在一起，路由器负责数据转发。
- **场景 C**：计算机通过 Internet 实现通信——Internet 是全球可达的通信网络，也是我们日常面对的网络环境。

这三个场景就是从零搭建一张网络的基本思路：先连线通起来，再逐步引入设备做转发，最终接入全球互联网。

**大型园区网络**的构建同样遵循"从需求出发逐层建构"的思路。一个典型的大型园区网分四层：

1. **接入层**：终端（PC、打印机等）通过交换机接入。比如教室里的交换机，教室之间不直连，统一通过楼栋机房汇聚。这样设计是因为教室间直连施工不便、线路长、故障排查无规律；统一汇聚后流量路径确定，故障排查有章可循。
2. **汇聚层**：楼栋之间通过更高性能的交换机再做一次汇聚，到达校园核心层，形成层次化网络。
3. **核心层**：校园网的中心节点，连接各楼栋的汇聚流量。
4. **出口层**：通过路由器连接外网（Internet/教育网），与运营商互联。

这里可以采用一个形象的工程类比——"先修路再管收费站"：先让线路连通，具体技术细节后面再展开。

**冗余设计**是网络可靠性保障的核心思想，定义很简单：两台终端通信时至少有两条路径可达。具体落地为两种形式：
- **设备冗余**：关键节点（如楼栋机房交换机、出口路由器）部署两台。
- **链路冗余**：关键链路至少拉两条线。

要不要做冗余，取决于故障影响面。PC 接入不做冗余？因为单台电脑故障只影响一个人，换了就好，损失可控。楼栋交换机与机房之间如果不做冗余，一条线路故障就影响整个教室乃至整层楼，可能构成教学事故。

> 【设计本源与技术哲学】："事件的严重程度决定了我们对其投入的保护成本。"

### 2.2 网络设备角色与部署方式

#### 核心原理

三种核心网络设备各有分工：

- **交换机**：组建中小型/大型园区网的主要设备。接口为二层接口（蓝色），连接终端；日常工作中大量刷交换机配置。组建内网主要靠交换机，数量远多于路由器。
- **路由器**：连接外网/广域网的设备。接口为三层接口（黄色），具有路由能力；支持 NAT、多种 VPN 技术（IPSec VPN、MPLS VPN、SSL VPN 等）、EVPN 等。注意：路由器接口只跑以太网技术，不支持 PPP/HDLC/PPPoE。
- **防火墙**：内外网之间的安全设备，支持防病毒、防垃圾邮件、入侵防御检测、上网行为管理等高级安全功能。启用高级安全功能时可能影响性能。

防火墙在实际网络中有三种部署方式，各有适用场景：

| 部署方式 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **直路部署** | 串联在出口路由器和核心交换机之间，做双机热备 | 所有内外网流量都经过防火墙，安全覆盖面全 | 开启高级安全功能时可能产生性能瓶颈；对现网改造复杂度高 |
| **旁挂部署** | 通过链路聚合旁挂到核心交换机 | 可按需引导流量（需安全防护的过防火墙，不需要的直接出去）；防火墙故障不影响整网通信；对现网拓扑影响小 | 需要额外策略配置引导流量 |
| **替代出口路由器** | 防火墙直接充当出口路由器 | 省钱 | 仅适用于外网线路均为同类广域网（如多家运营商 Internet 接入）；不适合广域网类型不一致的场景（如同时有 Internet、MPLS VPN 专线等） |

> 【设计本源与技术哲学】："人无完人，也没有完美的解决方案，一切以需求去思考问题——找到合适的最好。"

关于**数据中心**在网络中的位置：园区网可以单独建设数据中心机房，内部部署数据中心核心交换机（可做堆叠 CSS 或 M-LAG）和接入交换机。服务器通过多网卡做链路聚合连接到堆叠后的交换机（逻辑上变成一台交换机），同时实现网卡冗余和交换机冗余。

> 【设计本源与技术哲学】："网络设计优秀的地方——拓扑结构固定，但可以用不同技术去实现，技术与拓扑解耦。"

#### 易错点与考点

- 交换机 vs. 路由器分界：组建内网主要用交换机，连外网/广域网用路由器；路由器接口只跑以太网技术。
- 防火墙三种部署方式的选择逻辑是面试常见话题，关键在于"根据需求选方案"而非记住哪种最优。

### 2.3 网络参考模型与分层架构

#### 核心原理

网络功能如此复杂，必须分层定义，于是有了参考模型。

**OSI 参考模型**（开放系统互联，Open Systems Interconnection）将网络功能分成七层，从上到下为：

1. **应用层**：实现人机交互，提供产生/获取数据的入口。细分为**应用程序**（浏览器、微信/QQ、雷鸟/邮箱客户端、Putty/XShell，提供人机交互环境）和**应用协议**（HTTP、SMTP、POP3、Telnet、FTP、DNS、SSH，实现具体网络服务）。厂家可开发私有协议（如 QQ 的 OICQ）。类比：高速服务区。★此层主要由程序员把控，网工不需深入。
2. **表示层**：不同系统间数据格式的翻译/一致性，含加解密、压缩解压。> 【设计本源与技术哲学】："确保一个系统生成的数据在其他的系统上也能够理解并且识别。"网工不太关注。
3. **会话层**：通信双方间建立、管理、终止会话。具体体现：一款软件执行多项任务时任务间隔离且独立，比如一台迅雷同时下载多个文件、两台设备同时连一台设备产生两个会话需要隔离。类比：时间管理大师。
4. **传输层**：两大功能——①数据排序与可靠传输；②提高网络层 IP 地址的复用能力。
5. **网络层**：核心是**编址 + 寻址**，数据从源端发到目的端，并负责**路径选择**。传递数据的基础。类比：快递的收寄人地址、车牌、电话号码。路由协议就是为网络层服务的。
6. **数据链路层**：把数据封装成帧，在链路上做点对点/点对多点通信，进行**差错检测**。网络层宏观定义端到端，链路层定义链路上的微观逐跳转发（如从 1.1 到 2.2 需经 R1→R2→R3→R4 逐跳转发）。类比：唐僧取经九九八十一难、转机去美国——每次过一关/转一次机就是一跳。
7. **物理层**：在传输介质上把数据变成**比特流**（零和一），用光/电/无线信号表示。

上三层（应用/表示/会话）由应用程序统一提供，往下四层才是网工主要关注的领域。★初级岗位面试必问"OSI 哪七层"。

**OSI 与 TCP/IP 的对比**：OSI 网络层协议是 **CLNP**，编址协议是 **NSAP 地址**（网络服务访问点）；TCP/IP 网络层协议是 **IP**，编址协议是 **IP 地址**。两者作用相同、格式和叫法不同。★易错：IP 协议 ≠ IP 地址——IP 地址是 IP 协议的组成部分，本质上也是"网络服务访问点"能力的体现（类比：114.114.114.114 这个 IP 地址提供 DNS 服务；中美车牌格式不同，但功能相同——车辆身份标识）。

TCP/IP 是**事实标准**（"走的人多了就成了路"），OSI 是 ISO 的国际标准但实际应用不多。TCP/IP 标准模型是**四层**：应用层（OSI 上三层合一）、传输层（也叫主机到主机层）、网络层（也叫英特网层）、网络接入层（OSI 链路+物理合一）。但教学和实践中通常用**五层**模型与 OSI 对等比较。

常用协议按层归属速查：

| 层 | 协议 |
|---|---|
| 应用层 | FTP、TFTP、SNMP、DHCP、DNS、SMTP、HTTP |
| 传输层 | TCP、UDP |
| 网络层 | ICMP、IGMP、IP |
| 数据链路层 | PPPoE、以太网、PPP |
| 物理层 | 无协议概念 |

**标准化组织**：**IETF**（经 RFC 发布和取代协议，成员包括运营商、思科/华为等厂家、用户）；**IEEE**（定义全球约 30% 的标准，如 802.3 以太网、802.11 Wi-Fi）；**ISO**（定义了 OSI 参考模型）。

#### 易错点与考点

- ★考点：OSI 七层名称及顺序（初级岗位必问）。
- ★易错：IP 协议 ≠ IP 地址。
- ICMP 属于**网络层**，无端口号——端口号只给**应用层协议**使用。
- 通用协议 = 国家提供的公共服务，直接调用；私有协议只有本软件能用。

### 2.4 TCP/UDP 传输机制

#### 核心原理

传输层解决两个核心问题：数据怎么可靠地送到，以及一个 IP 地址怎么同时跑多个服务。

##### TCP 的选择逻辑

TCP 追求**可靠传输**。在选 TCP 还是 UDP 时，关键判断标准是业务类型：

- **非实时性业务**（FTP 传文件、收发邮件）：必须一次性成功、不能出错 → 选 TCP
- **实时性业务**（语音通话、视频通话、直播）：有容错能力、讲求效率 → 选 UDP

更深一层的规律：**单播**可用 TCP 或 UDP，但**广播/组播一定用 UDP**——因为信源很难逐一保证每个接收方都可靠收到，可靠性的风险"嫁接"到网络质量上。

> 【设计本源与技术哲学】："可靠本身是伪命题"——带宽够、设备好时很少丢包；丢包往往是因为带宽不够、线路老化、硬件质量问题、设备过载，而不是协议本身的问题。

##### TCP 三次握手（★面试高频）

三次握手的目的：传数据之前先确认对方有可靠传输能力，是一个**协商/获信**的过程，不传递实际数据。类比：投简历之前先考察对方靠不靠谱。

握手过程的报文交互（假设发起方随机序列号 = A）：

| 握手 | 方向 | 序列号 | ACK 号 | 标志位 | 说明 |
|---|---|---|---|---|---|
| 第一次 | 发起方 → 接收方 | A（随机） | 0 | SYN=1, ACK 比特=0 | 希望建立连接，第一个包无确认意义 |
| 第二次 | 接收方 → 发起方 | B（随机） | A+1 | SYN=1, ACK 比特=1 | 源/目标 IP 和端口互换（单通道一去一回"原目互换"规律）；ACK 号 = A+1 为**隐私确认**——正确返回 A+1 即完成确认，比原样回传更高效 |
| 第三次 | 发起方 → 接收方 | A+1 | B+1 | SYN=0, ACK=1 | 三次握手结束，双方确认了通信能力 |

★关键点：SYN 与 ACK 是两个独立的东西；三次握手不带应用数据；"加 1"是在无数据协商阶段的特殊处理（类比：先舔一口尝尝味道）。

##### 数据传输确认与编号（★口诀）

握手完成后进入数据传输阶段，确认规则变了：

> ★口诀：回送包的 ACK = 接收包的序列号 + 载荷字节数；回送包的序列号 = 接收包的 ACK。

发送方可以预判对方会回什么 ACK——对得上就是可靠收到，对不上就视为未收到。

数据段的序列号：首段序列号 = 初始序列号 + 1；下一段的序列号 = 上一段序列号 + 上一段的字节数（1 字节算 1）。例如载荷分别为 20、40、35 字节时，第二段序列号 = (A+1) + 20 + 40 = A+61。

**为什么要分段**：一份大数据切成多个载荷，某一段出错只重传那一段，提高容错率。类比：一碗粥掉进一颗螺丝，整碗不敢喝；一碗米饭掉进一颗，把那颗挑掉还能吃。

**重传机制**：发完一段后缓存中留一份副本，超时未收到对应 ACK 就重传，直到收到正确 ACK 才清空缓存。这也是 TCP 消耗资源的根本原因。形象工程类比：如同发邮件时在发件箱保留待确认副本，直到收到对方明确的已读确认才将副本销毁；若超时未收到确认，则从缓存中重新发送一份，直至确认到达。这也是 TCP 占用协议栈内存缓冲区的根本原因。

##### 滑动窗口（流控）

握手时双方互相告知缓存大小（窗口字段 = 一次能收多少字节），发送方按对方的窗口大小发送（可以拆成多段）。

上层应用取走数据后缓存变小，接收方回送当前可收大小，对方按新大小发——这就是窗口的"滑动"。窗口大小双方不必相同：>"我的能力我做主"。

发多了浪费带宽、发少了效率低，刚刚好最优。类比：微醺最舒服——不多不少恰到好处。

##### TCP 四次挥手（非重点）

关闭连接的过程：一方发 FIN=1+ACK=1 表示没数据了；对方回 ACK=1 仅表示"知道了，你没数据了"，**不代表断开**——对方可能还有话要发。对方也无数据时再发 FIN+ACK，收到最终 ACK 后才断开。

如果网络断了（扯网线/链路故障），无法走完四次挥手——靠**空闲超时**自动释放会话，不需要四次挥手。

TCP 耗资源的原因：服务器维护大量并发会话（百万用户同时发邮件），性能必然下降，所以需要适时断开释放资源。

##### UDP：重新认识

UDP 头部仅 8 字节（源端口 + 目标端口 + 长度 + 校验和），无序列号、无确认号、无三次握手、无流控。★适合一对多和单向传输——>"我想发就发，不管接收方"。

重新认识 UDP 的关键一句话：丢包不是 UDP 封装的问题，是网络质量不好导致的；UDP 只是缺少在网络差时维护可靠性的机制，本身高效、简单。选 TCP 还是 UDP，取决于业务对可靠性的要求和容错能力。

##### 端口号与五元组

端口号字段 16 比特 → 2^16 = 65536 个数 → 范围 **0~65535**：
- **源端口**：> 1023（≥ 1024），由会话发起方随机产生
- **目标端口**：0~1023 为**已知端口**（知名端口）——HTTP=80、HTTPS=443、Telnet=23、SMTP=25、POP3=110、FTP=21

端口号让一个 IP 地址可以同时提供多种服务、访问多种服务——极大提高了 IP 地址利用率。类比：地址上打许多洞/小孔，每个孔代表不同的会话——源端口让一个地址访问多种服务，目标端口让一个地址提供多种服务。

**五元组 = 源 IP + 目标 IP + 协议类型 + 源端口 + 目标端口**，可以唯一识别一个 TCP 会话。五元组相同的包属于同一会话（同一"流"）。

注意：源/目标 MAC 不参与会话标识——MAC 在链路层用于逐跳转发，传输途中会变。七元组/九元组要在具体场景才谈。

> 【设计本源与技术哲学】："了解问题、理解问题，比理解问题的答案更重要"——先搞清楚每个知识点用来解决什么问题。

#### 易错点与考点

- ★面试高频：TCP 三次握手——逐次讲清楚序列号/ACK 号/标志位即可达标。
- 易混：ACK 号 vs. ACK 比特；SYN vs. ACK。
- 易错：数据传输阶段不再固定"加 1"，改按载荷字节数确认；"加 1"仅用于无数据协商。
- 滑动窗口双方大小可以不同（"我的能力我做主"）。
- 收到第一个 FIN+ACK 后回 ACK 不代表断开——对方可能还有数据要发。
- FTP 是多通道协议（目标是 21 端口，源端口 20 不用于目标端口）。
- 网络断开无法走四次挥手时，靠空闲超时单方释放会话。

### 2.5 数据封装与解封装

#### 核心原理

数据从发出到接收，层层穿衣服、层层脱衣服——这是理解网络的最核心视角。

**发送方的封装流程**（从上到下）：

```
应用层 PDU（用户数据）
    ↓ 传输层：加 TCP/UDP 头
传输层 数据段（Segment）
    ↓ 网络层：加 IP 头
网络层 数据包（Packet）
    ↓ 数据链路层：加帧头（含 MAC）+ 帧尾（FCS）
数据链路层 帧（Frame）
    ↓ 物理层：加帧前导符，转换为比特流
物理层 比特流（0 和 1）
```

**接收方的解封装流程**正好反过来——从下往上，逐层剥头取出上一层的"载荷"。

这里有几个关键概念：

- **数据载荷（Payload）**：最终想要传递的信息本身。类比：网购包裹——你要的是游戏手柄（载荷），不是纸箱（外壳）。
- **报文（Packet，广义）**：网络中交换与传输的数据单元。> 【设计本源与技术哲学】："数据以报文为单位被设备进行处理。"类比：人体由细胞组成；网络数据虽然看起来是一串 0 和 1，但设备以报文为单位来组织处理。
- **头部（Header）**：加在载荷前面的控制信息。★一个报文可能有多层头部——TCP 头部、IP 头部、以太网帧头部……多次封装。
- **尾部（Trailer）**：加在载荷后面的控制信息（如帧尾的 FCS 校验）。
- **封装**：对载荷添加头部和尾部形成新报文。
- **解封装**：逐层剥掉头部和尾部，取出载荷。

**帧前导符**是一串固定比特（前 56 比特 10101010...，末 8 比特 10101011），标记帧的开头。设备收到前导符即准备接收帧。类比：火车进站鸣笛——鸣笛声就是前导符，告诉你"火车来了，准备上车"。各链路层协议的前导符不同，不携带实际信息，不是研究重点。

从**设备视角**看，不同层的设备"眼中看到的东西不一样"：

- **物理层设备**（集线器/Hub）：眼中只有 0 和 1
- **二层设备**（交换机）：按前导符把比特流组装成帧，**只读帧头、以帧为单位转发**
- **三层设备**（路由器）：先识别帧、剥掉帧头提取出 IP 包，再按目标 IP 查路由表转发——所以路由器也具有识别帧的能力

> 【设计本源与技术哲学】："没有规矩不成方圆"——各层字段长度事先定义好，设备就按这些规矩去读取和处理。>"最聪明的人搞出最傻逼的事"，把板上钉钉的字段搞清楚，网络就学好了。

**关于封装的类比**：解封装过程就像识别身份证——小孩（Hub）只看上面的数字（0/1），大人（交换机）能读懂含义；跑流程按规则来，谁也别越权。

#### ★★二层转发 vs. 三层转发（考点）

判定一个设备的转发行为是二层还是三层，**不是看设备名称，而是看它基于帧头还是基于包头转发**：

- 基于帧头转发 → 二层功能
- 基于 IP 包头转发 → 三层功能

三层交换机按帧头转发就是二层功能，按 IP 包转发就是三层功能。> "万变不离其宗，具体分析这个包在做二层转发还是三层转发。"

#### 易错点与考点

- 封装 vs. 载荷：报文 = 头部 + 载荷 + 尾部，设备以报文为单位处理。
- 头部多层封装：实际通信中头部不止一层（TCP → IP → 以太网），IA 阶段先建立概念。
- 二层/三层判定标准是转发依据（帧头 vs. IP 头），不是设备名称。

### 2.6 物理层与传输介质

#### 核心原理

##### 双绞线线序（★经典技能）

八芯颜色顺序：白绿、绿、白橙、橙、白蓝、蓝、白棕、棕。

两种线序标准：

| 标准 | 线序 |
|---|---|
| 568A | 白绿、绿、白橙、蓝、白蓝、橙、白棕、棕 |
| 568B | 白橙、橙、白绿、蓝、白蓝、绿、白棕、棕 |

- 两边都是 568A 或都是 568B → **直通线**
- 一边 568A 一边 568B（1/3、2/6 互换） → **交叉线**

**百兆**双绞线只用到 1/2/3/6 这四芯传数据。用测线仪看 1/2/3/6 灯亮就可以用，4/5/7/8 不亮百兆也能通（千兆不行——千兆八芯全用）。

##### 选线规则 + MDI/MDIX（★★重点）

传统规则：**相同设备用交叉线，不同设备用直通线**。例如 PC 连 PC 用交叉线，路由器连交换机用直通线。

但现在的设备普遍支持接口线序自适应（**MDI/MDIX**），直通线和交叉线都能用。注意：老思科设备不支持 MDI/MDIX，需要手动做交叉线；交换机上部分厂家可以关闭自适应功能。实验中凡遇到 PC 角色，均可视为一台路由器。

##### Console 线（全反线）

Console 线本质是**全反线**——八芯完全倒置互换（1↔8、2↔7、3↔6、4↔5）。电脑端通常接 USB，需要一个 RS232/USB 转 RJ45 的转接头。淘宝十几块钱直接买成品即可。

网工随身三件套：**测线仪、Console 线、螺丝刀**——类比理发师自带工具，到哪里都能干活。

##### 光纤与光模块

- **多模光纤**：橙色，传输距离短
- **单模光纤**：黄色，传输距离长（可达几十公里）
- 网线一般不建议超 80~100 米

光模块标签上有波长、传输距离等参数，据此判断单模/多模。模块上有 TX（发数据，发光）和 RX（收数据，收光），两端要交叉连接——你的 TX 接对方的 RX。模块上箭头向外 = 发送端，向内 = 接收端。

⚠️ 光纤是激光，不能长时间盯着看，瞟一眼确认有光就行。

##### Hub 与 CSMA/CD（★经典机制）

Hub 是集线器，表面看是星型结构，实际是**总线型**——所有接口共享同一条总线。多个主机同时发数据会导致总线上的信号碰撞，数据被破坏。类比：厕所门口几人同时进去撞在一起；酒吧里几个人同时大声说话谁也听不清。

CSMA/CD（载波监听多路访问/冲突检测）就是解决这个问题的机制：

1. 各主机先监听总线电压——有人在发就不发
2. 大家都监听到空闲且都想发 → 碰撞发生
3. 碰撞后 Hub 发 JAM 信号通知所有主机
4. 各主机执行随机退避算法（backoff），算出一个随机退避时间，时间到了再发，自然错开
   - 例：A 算 0.1s、B 算 0.25s、C 算 0.18s → A 在 0.1~0.18s 发完，C 再发，B 最后发
   - 越冲突，退避时间越长

**CSMA/CD 导致网卡只能半双工**——发的时候不能收，收的时候不能发。网卡本身有全双工能力，是机制不允许。主机越多→冲突越多→退避越频繁→每条主机能用的带宽越低→越传越慢。类比：20 个人的会议比 10 个人的会议结束得晚，因为争抢发言机会更激烈。

CSMA/CD 是基于总线约 1024 台主机规模设计的。理解大框架即可，不深挖退避时间和精确带宽分配。

##### 交换机 vs. Hub

交换机与 Hub 的根本区别在于交换芯片——交换机的每两个接口之间有**独立走线**（全互联），因此：

- 隔离冲突域（一接口 = 一冲突域），可以全双工，不需要 CSMA/CD
- 仍然不隔离广播域——广播帧会复制到所有接口

注意：交换机上如果某个接口连的是 Hub，则该接口需要调成半双工（可以通过自协商完成）。

★一个很实用的故障场景：以太网接口需要**相同速率 + 相同双工**，不一致就会丢帧/掉包。如果自协商失败，手动两边配成一致。类比：按教科书生病好治，不按教科书难治，要靠项目经验。可看华为案例库（故障宝典）。

##### 广播域判断（★重要）

**路由器接口隔离广播，交换机不隔离广播**。判断方法——想象法：在每条链路上想象一台电脑发出广播帧，这个广播帧能到达哪些接口？碰到路由器接口就停（被隔离），这些能互相收到广播帧的接口组成一个广播域。

典型例子：多台路由器互联的网络，每两个路由器之间是一条链路，加上路由器两侧的局域网，总共 5 个广播域。交换机加路由器组网，交换机一侧只有一个广播域。

#### 配置与命令

（本模块仅口头提及：速率/双工不一致时用命令手动调成一致；单个接口可修改双工模式。具体命令在后面涉及交换机配置的卷中展开。）

#### 实验与案例

百兆直通线测线仪测试：看 1/2/3/6 灯亮即可用。

华为案例库经典故障——"OSPF 邻居正常但学不到路由"，原因是网络类型不一致（一边广播型一边点到点型）。这是后续 IP 阶段的经典知识点。

#### 易错点与考点

- 百兆仅 1/2/3/6 传数据——4/5/7/8 不亮百兆可用，千兆不行。
- 速率/双工不一致致丢帧是常见故障——两边手动配一致。
- CSMA/CD 理解大框架即可，工程考试与实战中只需把握大框架，无需过度深挖退避时间精确计算。
- 多路访问（MA）是组网形态，泛洪是转发行为——完全不相干，不要混淆。
- Hub 与交换机都组建广播域，区别在于 Hub 对广播/单播/组播一视同仁全复制（只认 0/1），交换机二层能区分广播帧才复制转发。
- 网工必备三件套：测线仪 + Console 线 + 螺丝刀。

### 2.7 数据链路层与以太网

#### 核心原理

##### 多路访问 vs. 点到点

链路层组网有两种形态：

- **多路访问（MA - Multiple Access）**：一条链路允许多个接口接入，以太网是典型代表。因为多个设备共享同一链路，**必须在链路层定义地址来标识每个接口**，所以以太网有 MAC 地址。
- **点到点（P2P - Point to Point）**：一条链路只有两个接口、不允许第三个接入（如 PPP、HDLC）。因为没有寻址需求，**不需要链路层地址**——PPP/HDLC 没有地址概念。

这是理解"为什么要有 MAC 地址"的关键前提。

##### 以太网Ⅱ帧结构（★★必考）

以太网Ⅱ帧是链路层的核心数据结构。理论最小 64 字节、最大 1518 字节（考试按理论值 1518，实际有巨型帧超过此值）。

```
┌──────────────┬──────────────┬──────────────┬──────────────────────┬──────────────┐
│  目标 MAC    │   源 MAC     │    类型      │      用户数据         │    FCS       │
│   6 字节     │   6 字节     │   2 字节     │    46 ~ 1500 字节     │   4 字节     │
└──────────────┴──────────────┴──────────────┴──────────────────────┴──────────────┘
│←────────────────── 帧头 14 字节 ──────────────────→│                   │← 帧尾 4 字节→│
```

- 帧头 14 字节 + 帧尾 4 字节 → 比 IP 包多 18 字节
- 类型字段：**0800 = IP 包**、**0806 = ARP**（必须记住）
- IP 头 20、TCP 头 20、UDP 头 8、PDU 变长

帧前导符（共 8 字节）：前 56 比特为 10101010……交替信号，末 8 比特为 10101011，设备收到即准备接收帧。

##### MAC 地址（★★面试高频）

MAC 地址的结构：6 字节（48 比特），用十六进制表示。前 24 比特为 **OUI**（组织唯一标识符），由 IEEE 分配，厂家交钱申请（如华为、英特尔各有一个 OUI 段）；后 24 比特由厂家自行编号。

特性：**全局唯一、本地有效**——全球范围内不会重复，可以任意接入以太网而不怕冲突。类比：学号理论上全校唯一，但本校范围内区分即可；跨广播域后 MAC 冲突也无所谓，因为路由器会重写二层信息。

##### 有了 IP 为什么还要 MAC？（★★面试题）

> 交换机的二层转发不看 IP，只基于帧头 MAC 地址转发。多路访问链路需要在链路层区分每个接口，于是定义了 MAC 地址。点到点链路（PPP/HDLC）无寻址需求，所以没有地址概念。

简单说：IP 负责端到端寻址，MAC 负责链路上的逐跳转发。交换机和路由器各干各的活，缺一不可。

##### 帧类型判断（★经典题型）

判断一个帧是单播、组播还是广播，看**目标 MAC 地址的第 8 比特**：

- 第 8 比特 = 0 → **单播帧**
- 第 8 比特 = 1 → **组播帧**
- 48 比特全为 1（全 F） → **广播帧**

举例：第 8 比特为 5 → 二进制 0101 末尾 = 1 → 组播帧；全 F → 广播帧。

#### 易错点与考点

- ★面试题："有了 IP 为什么还要 MAC？"——答案要点见上，关键在"交换机二层转发不看 IP，必须靠 MAC 在链路层区分接口"。
- 看目标 MAC 第 8 比特判断单播/组播/广播——是看**目标 MAC**，不是源 MAC。
- 类型字段 0800（IP 包）/ 0806（ARP）必记。
- MAC 全局唯一、本地有效；跨广播域后 MAC 冲突不影响通信（路由器重写二层）。
- 点到点协议无 MAC 概念——因为没有多路访问的寻址需求。

## 三、总结

### 核心要点

1. **网络通信**是利用 IP 技术实现数据通信的过程。网络构建从需求出发逐层建构：接入→汇聚→核心→出口。
2. **冗余设计**的核心判断依据是故障影响面——影响的设备/人员越多，需要的冗余投入越高。
3. **OSI 七层**从上到下：应用层、表示层、会话层、传输层、网络层、数据链路层、物理层。上三层由应用程序统一提供，下四层是网工主战场。
4. **TCP/IP 是事实标准**，OSI 是国际标准但实际应用少。TCP/IP 可按四层或五层与 OSI 对照理解。
5. **TCP 三次握手**是传数据前的协商过程，不传应用数据；握手阶段每次"加 1"，数据阶段按载荷字节数确认。★面试高频。
6. **TCP 可靠、UDP 高效**。实时业务（语音/视频/直播）用 UDP，非实时业务（文件/邮件）用 TCP；广播/组播一定用 UDP。
7. **数据封装**从上到下：PDU → 段（Segment）→ 包（Packet）→ 帧（Frame）→ 比特流；解封装反过来。不同层设备眼中看到的"东西"不一样。
8. **二层 vs. 三层转发**的判定标准不是设备名称，而是基于帧头转发（二层）还是基于 IP 包头转发（三层）。
9. **以太网Ⅱ帧**帧头 14 字节 + 帧尾 4 字节；类型字段 0800 = IP 包、0806 = ARP；看目标 MAC 第 8 比特判单播/组播/广播。
10. **MAC 地址存在的原因**：在多路访问（以太网）的链路上，交换机二层转发不看 IP 只看 MAC，必须在链路层定义接口标识；点到点链路无此需求。

### 落地注意事项

- **ENSP 安装**：Windows 11 H24H2 不支持 ENSP（已知问题，暂无修复），建议 Win10 或 Win11 H23H2；安装次序 WinPcap → Wireshark → VirtualBox 5.2.44 → ENSP 主程序；不装 360 等杀毒软件，关闭 Windows 防火墙，开启 CPU 虚拟化，Win11 关闭 Hyper-V；VirtualBox 手动配置网卡地址须为 192.168.56.1。
- **双绞线**：百兆只用 1/2/3/6 四芯，测线仪看这四芯亮即可；千兆八芯全用。直通线/交叉线在现代设备上因 MDI/MDIX 自适应基本通用。
- **速率/双工不一致**是丢帧的常见原因→手动两边配一致。
- **Console 线**是网工标配，淘宝十几块直接买成品。
- **光纤**是激光，不能长时间盯着看。

- IA 学完后有综合实验，融合 IA 大部分知识点加部分 IP 内容，要能做到**只看需求、不看解法**独立完成。

| **OSI** | Open System Interconnection | 开放系统互联参考模型 | ISO 制定的概念性网络七层分层模型框架 |
| **TCP/IP** | Transmission Control Protocol / Internet Protocol | 传输控制协议/互联网协议 | 互联网事实上的通信协议栈标准架构 |
| **FCS** | Frame Check Sequence | 帧校验序列 | 以太网帧尾的 CRC 校验字段，用于差错检测 |
| **SYN** | Synchronize Sequence Numbers | 同步序列号标志位 | TCP 报文中用于初始化三次握手建立连接的标志 |
| **ACK** | Acknowledgment | 确认标志位/确认号 | 用于 TCP 可靠传输中的接收确认与流量控制 |
| **CSMA/CD** | Carrier Sense Multiple Access with Collision Detection | 载波侦听多路访问/冲突检测 | 早期以太网共享总线（Hub）争用介质与退避机制 |
| **OUI** | Organizationally Unique Identifier | 组织唯一标识符 | MAC 地址的前 24 比特，由 IEEE 统一分配给网络厂商 |
| **MTU** | Maximum Transmission Unit | 最大传输单元 | 数据链路层所能承载的最大网络层载荷大小（标准 1500 字节） |
